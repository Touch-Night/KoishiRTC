# QQ Linux ARM64 屏幕共享黑网格修复

QQ Linux ARM64 `3.2.34-53644` 的 PPAPI 视频渲染器使用两条专门的 Lanczos shader 绘制屏幕共享（NV12 / I420）。它们声明 `mediump float`，但插值权重使用的极小数在半精度计算中平方后变成零，导致 `0 / 0`。结果是规则黑色网格；原图坐标达到 1024 后，半精度无法保留坐标的小数部分，画面下方可全部变黑。

一次 864×1920 → 288×640 的接收案例中，理论边界为 `1024 / 1920 × 640 ≈ 341`，与实际约第 340 行开始的黑区吻合。离线半精度逐运算模拟还复现了上方亮行、黑行交替的位置。摄像头使用普通采样 shader，没有这一权重计算；摄像头发送的绿线需要独立排查。

## 修复方式

AV Host 启动时，先验证 QQ 版本、平台、架构以及原库 SHA256，再在自身 `runtime/native-video` 下生成副本。仅把两条已审计 shader 的精度改为 `highp`；字符串长度和库长度保持不变，总共改变 14 个字节。原 QQ 库不被覆盖。副本的相邻依赖和资源通过符号链接指回原 AVSDK 目录，保留 `$ORIGIN` 的加载语义。

| 检查项目 | 值 |
| --- | --- |
| Profile | `qq-linux-3.2.34-53644-arm64` |
| 原库 SHA256 | `07cf80b01fb42539ddc4d3a4e95853f26d51b8300ab0b7d4effe2986f1a6f34c` |
| 修复副本 SHA256 | `a67fbdf9aaf21a77759be2e9464b5718a84f21eb6135490cc5f085ef3abd946b` |
| NV12 shader 字节偏移 / 含终止符长度 | `0x1bc4d2` / `1554` |
| I420 shader 字节偏移 / 含终止符长度 | `0x1bcae4` / `1580` |

实现还验证每条完整 shader 的 SHA256、`weight4` 模式恰好出现两次以及生成库的完整 SHA256。不满足条件时不会应用补丁。已识别版本的补丁生成或完整性检查失败会停止 Host 启动，不会加载一份部分修改的库。其他平台和版本仍使用各自经过审核的原库，不会套用这两个偏移。

`/v1/status` 中的 `nativeVideoPatch` 会报告补丁编号、原库与实际加载库的 SHA256；`nativeProfile` 仍标识原始官方构建。`video.receiveSurface` 则报告接收画布和截图尺寸，可用于区分此 shader 问题与异步缩放、裁切问题。

项目及 npm 包只包含修复代码、审核数据和测试，不包含 QQ 的专有二进制库。安装器复制整个 `av-host` 目录，首次启动会在本机生成并校验副本；重复启动复用通过校验的副本。修改正在加载的库不会修复已有进程，因此升级后需要在通话结束时重启独立 AV Host。

## 原生证据

- `GLRender::InitNormalShader` 在 `0x4c0684…0x4c06c0` 直接使用上述两条内嵌 shader，而不是 AVSDK 的外部 `Shader` 目录。
- `GLRender::DoPaintNormal` 在 `0x4c42b4…0x4c4350` 为屏幕来源选择 Lanczos shader，为摄像头选择普通 shader。
- `ShareOutput::CopyNormal` 按各 YUV 平面的真实 stride 逐行拷贝；本次黑网格的周期和 1024 坐标边界来自 shader 精度，不是以浏览器缩放或 JPEG 编码解释。
- 自动回归覆盖精度数值、仅两处等长修改、版本/哈希/偏移检查、缓存幂等、依赖链接和不覆盖原库。
- 2026-10-06 本机真实通话复测：重启隔离 Host，状态确认加载上述修复 SHA；同一手机再次共享 864×1920 画面，返回 324×720 JPEG，画布与截图尺寸一致，黑网格和下半部黑屏消失，文字及整幅内容可见。此结果仅覆盖上述 Linux ARM64 构建，不代表其他平台或摄像头绿线已验收。
